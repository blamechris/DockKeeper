## Principles

- **Every behavioral requirement maps to one or more tests** (traceability table below). A requirement without a named test is a gap, listed as such.
- **macOS side effects live behind adapters; decision logic is pure.** We do not force unit tests around untestable side effects (moving the real Dock, `SMAppService`) — we wrap them and test the decisions (kickoff §7 rule). `MainDisplayPinner.decide` already follows this pattern (CONFIRMED); `DockAdapter` is the priority missing seam (TDD §4.3).
- **Behavior-focused test names**, e.g. `testDuplicateDisplayEventsProduceSingleRecoveryAttempt()`.
- **TDD development rule** for implementation work: (1) add/update the requirement → (2) write the failing test → (3) smallest passing change → (4) refactor → (5) run the relevant suite → (6) update docs when behavior or architecture changed.
- Framework: Swift Testing (`import Testing`, `@Suite`/`@Test`) — CONFIRMED in use.

## Test levels

### 1. Unit tests (fast, no system effects)

Targets: state reconciliation (`RecoveryCoordinator.decide` with synthetic events + simulated clock), display fingerprint matching/scoring/tie-handling/repair/migration, retry ladder and backoff, debounce/coalescing (generation counter), cooldown/oscillation budget, echo suppression, failure classification, orientation model mapping, settings persistence and migration, CLI argument parsing, `LoginItemManager.message(for:)` mapping.

Required seams (TDD §4.3): `DockAdapter` protocol with a recording fake (**missing in v0.1 — build first**); injected `applyMain` closure (exists — CONFIRMED); typed `DockEvent` values (post-M3 refactor); injectable clock for ladder/cooldown tests (PROPOSED).

### 2. Integration tests (real frameworks, isolated state)

Preferences persistence against isolated `UserDefaults` suites (pattern exists in `SettingsTests` — CONFIRMED); UUID→fingerprint migration on a populated suite; coordinator + monitor with mocked adapters driven by synthetic event sequences; CLI end-to-end against an isolated defaults domain; external-defaults-change observation (DK-FR-007-S3).

Each row records: pass/fail, macOS version, which bundle paths were registered at the time, and the exit path observed (stderr notice / log line / neither). Note that **`open`'s exit status is not evidence** — it returns 0 whether the launch survived or was deflected (measured), so every row must be checked by counting menu-bar icons or live pids. **A deflected launch also exits 0** (measured 2026-08-18; `SingleInstance` exits `EXIT_SUCCESS` deliberately, so a login item that correctly deferred does not read as a failed launch), so exit code cannot distinguish "ran" from "yielded" either.

Two measured properties of a directly-`exec`ed bundle binary drive the design of rows 7–7c and are easy to get backwards.

- **It registers.** `lsappinfo` reports it with an ASN, `bundleID`, `bundle path`, `type="UIElement"` and a checkin time — it is a first-class running instance of *that bundle*, not an anonymous process. So an `open` naming the **same bundle** is substituted onto it rather than launching (row 7b), and the guard never runs. This does **not** generalise to row 5: LaunchServices keys its already-running test on the bundle's **inode**, so a second copy at a different path (`dist/`) is a different application, is not substituted, and does reach the guard. Same-bundle and different-bundle are different tests, which is why 7b and 5 both exist. **Both halves are now confirmed on-device (2026-08-18)** — row 5's newcomer appears in the unified log as `Duplicate launch: … exiting` in three separate runs, and row 7b's `open` produces no such line, in a window where the immediately following 7c direct-exec does.
- **It stays dateless.** Its `NSRunningApplication.launchDate` is `nil` for its **entire lifetime**, so a peer that is one of these must have a kernel start time substituted before it can be ranked at all (row 7c).

Registered-but-dateless is one state, not two, and a row that exercises only half of it tests something other than what it claims — which is exactly how 7b's stated purpose drifted from its actual coverage.

### Use the unified log. `ps` sampling cannot see a deflected launch.

**This is the most important line in §3b, and it was learned by getting row 5 wrong.** A deflected newcomer exits inside `App.init()` — before `NSApplication` exists, before it checks in with LaunchServices, milliseconds after `exec`. Therefore:

- **`ps`/`pgrep` polling does not catch it.** 800 consecutive samples across an `open` caught nothing while the unified log showed the newcomer spawning and being deflected in that exact window. Absence of a sampled pid is **not** evidence that nothing launched.
- **`lsappinfo` does not show it either**, for the same reason — it never lives long enough to check in. "Never checked in" is not "never launched".
- **`open`'s exit status is 0 regardless**, as this section already records, and a deflected launch also exits 0.

Every one of the obvious instruments is blind to the exact event these rows exist to observe. The unified log is not:

```bash
/usr/bin/log show --predicate 'subsystem == "com.dockkeeper.app" AND category == "app"' --last 10m --info
```

A deflection appears as `Duplicate launch: pid <incumbent> already running; exiting`, emitted by `SingleInstance` immediately before it exits. Its **presence** proves the guard ran; its **absence across the window** is what proves LaunchServices substituted instead — which is how 7b and 5 are actually told apart.

**Use the absolute path `/usr/bin/log`.** In `zsh`, `log` is a **shell builtin**, so a bare `log show …` hits the builtin and fails with `too many arguments` and no output. Two separate sessions read that as "the unified log is unavailable in this environment" and recorded it as a standing fact; it was never true, and believing it is what left `ps` sampling as the instrument of record long enough to produce a wrong conclusion.

A **third** registration state, measured 2026-08-18 while running row 9, completes the set — and it is what collapses both halves of DK-FR-012 S7 into a single fact rather than two independent ones. An unbundled build *also* checks in with LaunchServices: `lsappinfo` gives it an ASN, `type="UIElement"`, a bundle path pointing at the bare binary, and a checkin time. What it does **not** get is an identifier — `bundleID=[ NULL ]`, `Version=[ NULL ]`. From that one omission both halves follow:

- **Not blocked**, because `SingleInstance.yieldIfDuplicate()` returns early on `Bundle.main.bundleIdentifier == nil` — it never reaches a comparison.
- **Not detected**, because `NSRunningApplication.runningApplications(withBundleIdentifier:)` has no identifier to match it against. Confirmed from the outside, which is the only way it can be: a *third* process running `--diagnostics` during the overlap listed the bundled incumbent and not the unbundled peer, though both were alive at that instant.

So the three states are: **LS-launched bundled** (identifier, path, `launchDate`), **direct-`exec`ed bundled** (identifier, path, no `launchDate` — rows 7–7c), and **unbundled** (no identifier at all, hence invisible to every bundle-ID query — row 9). Reading "unbundled" as "unregistered" is the easy mistake, and it is wrong: it registers, it simply registers anonymously. The distinction matters for any future guard that reasons about peers by something other than bundle identifier — such a guard would start seeing `swift run` builds, and DK-FR-012 S7 says it must not.

Two cautions for whoever runs the rest of this matrix, both learned the hard way:

- **Probe bundles outlive the session that made them.** A `Probe.app` from an earlier session was still checked in with LaunchServices, and still running, 37 minutes after that session ended. It was harmless only because it claimed `com.example.dkprobeapp`; a probe that reuses `com.dockkeeper.app` would have silently contaminated every row above. Check `lsappinfo list | grep -B2 'bundleID="com.dockkeeper.app"'` before trusting a result, and expect exactly one entry.
- **Rows 6, 8 and 9 need no build gate and no second account.** They were previously grouped with the blocked rows; they are not. Rows 3, 4 and 5 do need the incumbent quit, and were run that way on 2026-08-18. Only rows 1 and 2 are left, and neither is blocked on tooling — they need a second local account and a real logout.

### 4. Reliability tests

100 consecutive restorations (no oscillation, no leak); repeated sleep/wake cycles; rapid display connect/disconnect storms; resolution change during an in-flight restoration; preference change during restoration; app relaunch during pending recovery; 24 h idle (CPU ~0%, memory flat, log growth bounded) — the DK-NFR-001 measurement gate (M6).

### 5. CI gates (PROPOSED)

`swift build && swift test` on a macOS 14 runner; release builds additionally: `Scripts/build-app.sh` succeeds, `codesign --verify` passes, and a **no-networking-symbols check** (scan the binaries for `NSURLSession`/`Network.framework` references) enforcing DK-NFR-002 by construction.
